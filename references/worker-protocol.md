# Worker 分发协议

L2 多 worker 并行执行能力默认关闭，默认路径为串行实现，但队列盘点、触发条件重估和可开工项通报等并行义务始终有效。只有用户明确要求并行、任务边界清晰且文件范围不重叠时，才可启用并行执行。执行体类型、可见性和兜底规则先按 [collaboration-governance.md](collaboration-governance.md) 裁决；无目标政策时主会话串行。

## 1. 启用前检查

1. 用户明确要求并行执行。
2. 方案已确认，并已拆成多张 WO。
3. 每张 WO 已通过共享 registry 分配编号。
4. 每张 WO 有独立分支和明确 base。
5. 每张 WO 的允许修改文件清单互不重叠。
6. 依赖关系和合并顺序已声明。
7. 目标仓库执行体政策已读取并可执行。
8. 执行体启动、留痕和收口方式已确定。

任一条件不满足时主会话串行、停止询问或登记延期，不得降级成伪并行。

## 2. 主会话职责

主会话是唯一调度和收敛点：

1. 统一分配 WO/TD，不允许多方发号。
2. 检查文件范围、依赖和分支冲突。
3. 按目标政策选择 `main-session-serial`、invisible executor、native visible child 或 independent worker。
4. 生成标准化 worker prompt。
5. 保存执行体身份、启动方法、实际模型、边界、输入版本和输出位置。
6. 跟踪 `running / completed / failed / interrupted`。
7. 执行结束后记录关闭、归档或逻辑收口证据。
8. 只基于产物和验收结果收敛结论。
9. 汇总共识、分歧、证据缺口和后续动作。

## 3. 多工单并行开发义务

### 效果优先于并行效率

1. 分发方必须主动识别可开工项，但不得为追求并行数量牺牲正确性、证据完整性或发布安全。
2. 判定核心、证据链、发布路径上的工单该串行就串行；即使文件清单暂时不重叠，也要先判断语义依赖。
3. 文件面交叠的候选并行任务，分发前先对齐切图并重新划定不重叠范围；无法可靠切分时错开范围或串行，禁止边做边争用文件。
4. 并行义务不等于默认并行执行。未获得用户明确确认时，仍应盘点、发号并按默认串行路径推进，不得空等。

### 队列不空转

1. 队列空闲时，分发方必须主动盘点已确认方案、已发号 WO、被依赖项和可立即开工项。
2. 盘点出可开工项后，由主会话统一发号并推进默认允许的串行任务或已获授权的并行任务，不以“没有新指令”为由停工。
3. 盘点不出可开工项时，必须通报「队列空 + 阻塞原因」，列出待用户决策、待材料、依赖未满足或执行体不可用等具体原因。
4. 分发方应维护候选项、在途项、阻塞项和下一动作的可见清单；不得用未经验收的结果填补队列。

### 触发条件自动重估

1. 挂有触发条件的待办、方案和工单，在条件相关事实变化时必须重新评估，不能只在创建时判断一次。
2. 代码合入、材料到位、依赖完成、政策确认、工具恢复或用户裁决后，分发方应检查关联触发条件并记录结果。
3. 条件已经满足而无人回头检查，视同治理违规；应立即登记、恢复推进或说明新的阻塞，不得继续保持无依据的等待状态。
4. 重估不等于自动扩大范围或跳过方案确认；条件满足后仍按目标仓库政策执行。

### 子代理执行与主会话让位

1. 可委派的实现任务优先交给符合目标政策的真实子代理执行；主会话负责范围裁决、发号、监控、证据核对和收口。
2. 分发会话不得长时间占用自身窗口跑实现细节，导致其他在途任务无人监控或无人收口。
3. 主会话让位不等于放弃责任；子代理失败、超范围或证据缺失时，主会话必须停止相关推进并显式处理。
4. 子代理身份、无 fallback 路径和关闭证据按 collaboration-governance 执行，不得用主会话补写代替真实执行。

### 并行度约束

1. 并行开发、串行合并；热点文件同一时间只允许一个写入方。
2. 在途工单上限由治理要求与分发方根据仓库风险、验证容量和收口能力商定，并向参与者通报；不得无上限分发。
3. 达到上限、关键证据积压或热点文件争用时，停止新增分发，优先完成监控、验收和合并收口。
4. 合并窗口按 [merge-protocol.md](merge-protocol.md) 执行；并行实现不代表可以批量跳过复验。

## 4. Worker Prompt 契约

每份 prompt 必须包含：

```text
WO 编号
TD 编号
仓库路径或 worktree
分支名
base commit 或 base branch
允许修改文件
禁止修改项
行为变化边界
架构边界
配置边界
验收命令
输出位置
停止条件
```

使用 [worker-prompt.template.md](../assets/templates/worker-prompt.template.md) 生成，未填字段不得分发给 worker。

Worker 输出必须包含架构影响、配置影响、是否触及屎山或兼容层，以及对应证据；不得只写“无影响”。

## 5. Worker 禁止事项

1. 自行取号或推导编号。
2. 修改共享 registry。
3. 扩大允许修改范围。
4. 修改其他 WO 的文件。
5. 创建、合并、rebase 或删除分支。
6. 声称完成但未运行验收命令。
7. 将技术缺口改为业务通过。
8. 伪装独立评审或冒充其他 worker。

发现范围外问题时，worker 只登记发现并停止相关部分。

## 6. 执行体要求

1. Worker 必须是真实模型执行体，不能由主持人自答、普通命令输出或后台进程替代。
2. 目标仓库要求不可见执行体时，不得改用可见 worker。
3. 目标仓库首选 native visible child 时，必须记录原生 child 证据和父子关系。
4. `thread/start` 等独立会话是 independent worker，不得登记为 native child。
5. 只有真实 child 启动失败才允许一次性 fallback，并记录失败证据、原因和 worker 身份。
6. 模型选择遵循用户显式配置或目标仓库规范；没有配置时先询问。
7. 每个 WO 只绑定一个执行体；重启或兜底必须追加记录。

## 7. 分发留痕

每次分发记录：

```text
WO：
TD：
executor_type：
launch_method：
executor_id：
visibility：
模型：
parent_execution_id：
subagent_start_status：
仓库/worktree：
分支：
输入版本：
输出位置：
状态：
开始时间：
结束时间：
收口证据：
```

状态只允许：

```text
running / completed / failed / interrupted
```

## 8. 收敛规则

1. 逐张 WO 检查范围内文件和验收结果。
2. 任一 worker failed 或 interrupted 时，不声称整体完成。
3. 出现矛盾结论时先列证据和分歧，不直接择优。
4. 需要圆桌时按 [roundtable-protocol.md](roundtable-protocol.md) 另行安排；不把单 worker 输出称为圆桌。
5. 主会话不得代填 worker 验收结果。
6. 全部合并前保持 registry 中对应 WO 为 active；验收和收口完成后再 complete。
