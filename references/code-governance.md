# 配置与架构代码治理

本参考把配置治理和代码结构治理纳入 L1 基线。目标不是追求抽象层次，而是防止配置散落、入口巨石化、依赖反向、外部调用失控和兼容层无限保留。

## 1. 配置治理

### 1.1 配置分类

修改或新增配置前，先判断类别：

| 类别 | 示例 | 治理要求 |
|---|---|---|
| 运行行为参数 | 并发、批次、队列、重试、超时、轮询、等待上限 | 统一配置入口，可验证、可回放、可回归 |
| 功能开关 | 新路径启用、降级、实验开关 | 记录 owner、默认值、退出条件 |
| 环境标识 | dev/test/staging/prod、区域、租户 | 只描述环境，不复制业务规则 |
| 外部端点 | API base URL、服务地址 | 提交 example，运行值由环境注入 |
| 凭据和敏感材料 | password、token、key、证书 | 独立 secret 管理；不得提交、复制或输出 |
| 本地工具路径 | 解释器、浏览器、办公软件路径 | 允许环境覆盖，记录发现顺序 |
| 一次性调试参数 | debug flag、临时采样、诊断范围 | 显式命名并限制生命周期，不得变成隐式生产配置 |

### 1.2 唯一事实源

每一类配置必须有一个主事实源：

```text
配置类别
主配置文件 / 配置对象
提交的 example 或 schema
运行时来源
覆盖优先级
安全默认值
校验方式
负责人或 owning module
```

禁止同一运行参数同时由多个互不知情的来源控制。目标仓库已有配置框架时优先沿用该框架；本参考不强制 `.env`、YAML、TOML 或某种语言专属 API。

### 1.3 提交与运行边界

1. 仓库提交 example、schema、默认值和校验逻辑。
2. 本地或生产运行值不入 Git，除非仓库明确声明该值非敏感且环境无关。
3. secret 只进入 secret manager 或本机受保护运行时；不得出现在 example、日志、报告、测试快照或备份说明中。
4. example 必须可启动或可解析，不携带真实端点和凭据。
5. CI 至少校验配置 schema、必填项、类型、取值范围和非法组合。

### 1.4 优先级与默认值

配置优先级必须显式，推荐：

```text
显式一次性诊断参数
  > 进程环境变量
  > 环境配置文件
  > 仓库默认配置
  > 代码安全默认值
```

要求：

1. 每层覆盖关系可测试。
2. 业务代码只消费解析后的配置对象。
3. 并发、超时、重试、批处理等参数不得硬编码在业务分支中。
4. 安全默认值必须选择保守行为；缺配置不得变成无限制、无等待或自动通过。
5. 配置变化必须有测试或可复现实验证明影响。

### 1.5 工单配置影响

触及以下内容时，工单必须声明 `配置影响=有`：

1. 新增或修改配置键。
2. 改变默认值、优先级、来源或校验。
3. 把常量、环境变量或 CLI 参数改成配置。
4. 改变 secret 或端点注入方式。
5. 改变性能、并发、重试、超时或批处理行为。

声明为无影响时，必须确认没有新增魔法参数、隐藏默认值或一次性环境变量。

## 2. 架构与依赖治理

### 2.1 通用分层

除非目标仓库已有更合适模型，默认使用单向分层：

```text
Interface / Entry
  -> Application / Use Case
  -> Domain / Policy
  -> Infrastructure / Adapter
```

职责：

1. Interface / Entry：CLI、HTTP、UI、Job 入口，只做参数解析、帮助信息、鉴权上下文和命令分发。
2. Application / Use Case：编排步骤、事务边界、状态迁移和失败封口，不实现领域规则。
3. Domain / Policy：业务规则、状态判断和值对象，不直接发起网络、数据库、文件系统或子进程副作用。
4. Infrastructure / Adapter：数据库、HTTP、模型服务、消息队列、文件系统、子进程和外部工具。

### 2.2 依赖硬规则

1. 依赖方向必须从外层向内层，禁止反向导入。
2. 领域层不得直接发起外部 IO。
3. 入口不得内联业务规则、报告组装或多阶段编排。
4. 共享公共层不得依赖业务模块。
5. 禁止循环 import、循环模块依赖和通过动态加载隐藏依赖。
6. 外部调用统一经过 adapter/gateway，并记录超时、重试、取消、错误分类和可追溯 ID。
7. 投影、报告或 UI 层只读状态并呈现结果，不得反向修改判定或业务状态。
8. 状态迁移必须集中在显式状态机或编排服务，不得由多个模块隐式改动。

目标仓库已有架构规范时，先诊断并沿用其命名；本参考只补缺失底线。

## 3. 巨石代码治理

### 3.1 识别

出现以下证据时识别为巨石风险：

1. 一个入口同时承担参数解析、编排、业务规则、外部 IO、状态和渲染。
2. 文件、类或函数承担多个不相关职责。
3. 修改任一业务都需要理解大量无关代码。
4. 测试只能从巨型入口端到端执行，无法局部验证。
5. 同一职责存在多个影子副本或嵌套复制。
6. 大量兼容 shim 没有删除条件。

识别时记录：

```text
对象路径
职责列表
规模或复杂度指标
顶层函数 / 方法 / 赋值 / 分支等可用指标
外部调用点
测试覆盖方式
重复或影子副本
迁移候选
```

不设置跨语言统一行数阈值。阈值必须来自目标仓库现有工具、团队约定或基线统计，并写明统计口径。

### 3.2 基线与 ratchet

巨石治理先建立不可变基线，再启用 ratchet：

1. 单个巨石对象规模或复杂度不得上升。
2. 已识别巨石聚合规模不得上升，防止一个缩小、另一个膨胀。
3. 巨石内新增文件或影子副本直接视为聚合增长。
4. 正确性紧急例外必须经用户确认，并优先委托、拆分或净删除。
5. ratchet 报告必须绑定 commit、统计口径和输入文件集合。
6. 自动门禁默认不启用；启用前必须有单独方案和验收。

### 3.3 新增行为规则

已识别巨石内禁止继续新增业务逻辑。可选做法：

1. 新逻辑放入边界清晰的新模块或已有领域模块。
2. 巨石入口只保留薄 adapter、参数转换和委托。
3. 迁移必须按行为切片，不做一次性大重构。
4. 迁移前先为外部行为建立 characterization test。
5. 新模块必须有直接测试和失败语义。
6. 迁移期间旧行为与新路径用同集输入对照。

## 4. 兼容层与影子实现

1. 每个 shim 必须记录原因、替代路径、删除条件和承接工单。
2. 影子包、影子模块和嵌套副本必须登记引用关系和差异状态。
3. 动态 import 别名只能作为显式登记的迁移机制，不得成为长期路由。
4. 兼容层不得反向依赖新领域实现内部细节。
5. 目标实现接管后，兼容层只能保留最小转发，不得重新积累业务规则。
6. 没有删除条件的兼容层视为结构债务，必须进入开放事项。

## 5. 工单架构影响

触及以下内容时，工单必须声明 `架构影响=有`：

1. 入口、模块边界或公共接口。
2. 依赖方向、循环依赖或动态加载。
3. 外部 IO、子进程、网络、数据库或消息调用。
4. 状态机、事务边界或失败封口。
5. 数据 schema、稳定产物格式或跨模块契约。
6. 巨石入口、已识别巨石基线或兼容层。
7. 性能结构，例如队列、并发、缓存、批处理或重试归属。

工单需回答：

```text
改动属于哪一层：
依赖方向是否变化：
是否扩大巨石：
外部调用是否绕过 adapter/gateway：
兼容层删除条件：
测试落在哪个边界：
```

## 6. 诊断与验收

已有仓库先诊断 lint、format、typecheck、import/architecture 工具和现有配置框架。诊断输出必须区分：

```text
事实：当前代码和工具观察到什么
约束：仓库显式规范要求什么
偏差：登记到哪个工单或待办
```

验收至少包含：

1. 目标仓库已有 lint/type/architecture/import 检查。
2. 配置优先级和默认值测试。
3. 新模块直接测试。
4. 巨石迁移的旧行为对照。
5. 依赖方向没有新增反向或循环依赖。

结构检查不能替代业务测试、安全评审、运行验证或发布验收。
