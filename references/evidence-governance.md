# 数据与证据目录治理

本协议隔离验收输入、预期结果和运行产物，防止答案泄漏、跨用例污染和历史产物被误当作事实。目标仓库可以使用不同目录名，但必须在方案或工单中建立唯一、明确的角色映射。

## 1. 三类目录职责

| 目录角色 | 通用示例 | 唯一职责 | 禁止用途 |
|---|---|---|---|
| 输入语料 | `data/inputs/` | 保存经确认、可追溯的原始输入及其必要元数据 | 放预期答案、历史运行输出或由其他用例拼接的输入 |
| 预期结果 | `data/expected/` | 只保存验收对照用预期结果、容差和判定说明 | 进入生产输入、运行参数、检索语料、训练样本或提示词 |
| 运行产物 | `outputs/` | 保存单次运行生成的报告、日志、中间结果和运行元数据 | 反向成为输入、预期结果、独立通过证据或新基线 |

目录角色不得混用。目标仓库已存在等价目录时保留其路径并记录映射，不为套模板强行移动数据。

## 2. 预期结果边界

1. 预期结果只用于运行完成后的独立验收对照，永不进入生产输入或提示词。
2. 不得把预期结果注入 system、developer、user、工具上下文、检索索引或少样本示例。
3. 不得根据预期结果修改当次输入、提示词或中间产物，再宣称独立通过。
4. 验收脚本读取预期结果时，应与生产执行路径隔离，并在运行记录中说明读取边界。
5. 需要调试定位时，只能引用偏差位置和必要片段，不得把整份预期结果回灌执行体。

## 3. 用例与运行隔离

1. 每个用例只能使用自身声明的输入和预期结果，禁止跨用例拼接输入、答案、日志或产物。
2. 一个用例失败时，不得从其他用例借材料补齐，也不得合并多个用例结果掩盖失败。
3. 每次运行必须有独立输出标识，记录输入版本、代码或配置版本、开始时间和执行状态。
4. 复跑使用新的运行产物位置或明确追加记录，不覆盖历史失败证据。
5. 禁止把历史 `outputs/` 或其派生副本作为后续运行输入、独立通过证据或基线；只有重新确认并登记的原始事实源和预期结果才能承担相应角色。历史输出保留为失败记录或故障调查线索，不得删除或改写成通过证据。

## 4. 证据清单与 fail-closed

工单涉及数据、模型、解析、验收或报告产物时，应提供证据清单：

```text
输入目录：
输入版本或校验值：
预期结果目录：
本次运行产物目录：
运行标识：
生产输入与预期结果隔离检查：
跨用例隔离检查：
历史 outputs 排除检查：
缺失材料：
```

1. 缺少输入、预期结果、原始材料、访问权限或必要运行记录时，一律 fail-closed。
2. 不造数、不用样例冒充真实材料、不用历史产物替代缺失材料、不跳过缺失项后声称全量通过。
3. 无法判断目录职责或材料来源时保持需确认，先询问材料责任人。
4. 证据清单缺失不等于验收不适用；应明确说明为何本工单不涉及数据证据。
5. 报告只能引用本次运行产物和已登记事实源，历史输出只可作为故障调查线索，不能作为通过证据。
