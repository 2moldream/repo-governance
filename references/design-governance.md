# 详细设计治理

本协议治理详细设计影响声明、设计增量事实源和服务接口地图。详设影响声明与必要的增量声明义务随 L1 基线启用；自动台账、生成视图和接口检查工具默认关闭，启用前必须单独设计并确认。

## 1. 详设影响声明

每张 WO 必须在实施前填写：

```text
详设影响：有 / 无 + 理由
设计章节：
design_delta_ref：
```

1. `详设影响=有` 时，必须列出受影响的详细设计章节、接口或模块，并追加对应 design-delta entry。
2. `详设影响=无` 时，必须给出可核查的理由，说明为何不改详细设计；只写“无影响”不算理由。
3. 触及接口契约、跨模块调用、数据或状态生命周期、权限、安全、发布、迁移、回滚等高风险路径时，不得声明 `详设影响=无`。
4. 实施中发现影响超出原声明时，停止相关实现，更新方案、工单和设计记录后再继续；不得事后补一句声明掩盖范围扩大。
5. 详细设计治理不能替代架构影响、配置影响和关键治理文档评审；各声明分别判断。

## 2. design-delta 增量台账

目标仓库有详设变更时，必须在方案或工单中指定唯一增量记录位置；启用专门台账时，还应指定当前完整详设的位置。未启用专门台账的，在工单中追加同字段 entry 并填写 `design_delta_ref`；确无详设变更时填 `不适用 + 理由`。design-delta 只记录相对当前详设的增量，不复制整份设计，也不反向把未合入方案当成当前实现。

台账是 append-only 事实源：

1. 已提交 entry 不得修改、删除、压缩或重排历史。
2. 纠错、撤回或替代必须新增 entry，并引用原 entry 和原因。
3. entry 必须先关联已确认的 WO/TD 和方案，再允许实现引用。
4. 合入后由对应设计文档或生成视图承接；历史 entry 保留，不因其已承接而删除。

每个 entry 至少包含：

```text
entry_id：
WO/TD：
影响类型：新增 / 修改 / 纠错 / 撤回 / 替代
域：
设计章节：
变更摘要：
code_map_ref：
验收引用：
决议引用：
前置 entry：
状态：
```

字段没有适用对象时，应记录 `不适用 + 理由`，不得凭空编造引用。决议引用必须指向用户、架构责任人或目标仓库指定决策者的可追溯确认。

## 3. 服务接口地图

服务接口地图是接口与服务契约的生成视图，不得手工维护成第二事实源。地图至少能追溯到提供方、消费方、契约定义、code map 节点和对应设计章节。

启用接口地图治理后，以下情况全部 fail-closed：

1. 生成视图 stale：地图与当前契约、代码或生成元数据不一致，或没有可证明的新鲜度。
2. 外键缺失：提供方、消费方、契约、code map 节点或设计章节的必需引用不存在。
3. 接口治理 finding 未解决：包括未登记接口、方向冲突、契约不一致、责任方缺失和已禁用的隐式调用。

处理要求：

1. stale 时重新从事实源生成并复核，不直接编辑生成结果掩盖漂移。
2. 外键缺失时补齐真实事实源和引用；不得用占位节点或猜测关系通过检查。
3. finding 必须关联承接 WO/TD 和关闭证据；未关闭前不得声称接口治理通过。
4. 检查工具不可用、输入不完整或地图未生成时，结果保持需确认，不默认通过。
5. 未启用自动接口地图时，工单仍需声明详设影响；人工查看代码不能冒充生成视图检查。

## 4. 与验收的关系

详设影响声明、design-delta entry 和接口地图结果都是验收证据的一部分。验收等级按 [acceptance-governance.md](acceptance-governance.md) 单独裁决；补齐设计文档不等于完成代码验收，测试通过也不等于消除设计漂移。
