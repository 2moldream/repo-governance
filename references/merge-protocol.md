# 分支合并治理协议

集成分支是长期事实源。实现分支只有完成范围检查和验收后，才能由主会话合并；worker 不得合并。

## 1. 合并前检查

按顺序执行并记录结果：

1. Registry `validate` 通过。
2. WO 状态为 `active`，placeholder 已登记。
3. 分支名、base、worktree 与 registry 记录一致。
4. worktree 无未提交文件。
5. 分支相对 base 有实际变更。
6. 变更文件均在 WO `范围内文件`。
7. 行为变化声明完整。
8. 工单 `实施与验收记录` 无待执行、待补或失败结论。
9. 验收命令已逐条运行并记录结果。
10. 依赖 WO 已按顺序合入。
11. 集成分支自 base 之后的变化已审查，冲突风险已识别。

任一条件失败时 fail-closed，不合并。

## 2. 合并顺序

1. 无依赖且无文件重叠的 WO 可按完成先后合并。
2. 依赖任务先合并被依赖项。
3. 文件范围重叠任务必须串行；后合并者基于最新集成分支重放验收。
4. 跨模块改动优先合并边界清晰的小工单。
5. 高风险发布、Schema、迁移和安全改动最后单独合并。

## 3. 合并攒批窗口

多张工单在同一集成窗口合并时，攒批不能降低任何一张工单的验收要求：

1. 同族工单必须串行合并。共享核心判定、证据链、事实源或发布路径的工单属于同族，不因文件暂时不重叠就变成异族。
2. 异族工单只有允许修改文件不重叠，且事实源、配置、生成视图和行为语义均无冲突时，才可进入同一攒批窗口。
3. 每批按其中最高验收等级复跑验收；一张 L2 工单与多张 L0/L1 工单同批时，整批必须满足 L2，不能只复跑低等级检查。
4. 每批记录成员工单、合并顺序、实际合并提交、最高验收等级、命令输出和事实源冲突检查。
5. 出现冲突、非预期漂移、范围外变更或任一验收失败时，立即停止攒批；不得继续合入后续成员来稀释失败。
6. 失败批次保留已产生的证据，修复后重新执行整批复验；不能沿用失败前的“通过”结论。

## 4. 稳定分支保护

1. stable main 禁止 force push，禁止通过改写公开历史消除冲突或失败证据。
2. 推进 stable main 前记录当前 baseline commit 和可执行回滚点；回滚点必须能定位到推进前的集成分支状态。
3. 每次推进后记录新 commit、关联批次和验收结果；回滚按目标仓库政策使用可审计的新提交，不伪装成未发生。
4. 禁止以攒批、追平分支或修复检查为由绕过稳定分支保护。

## 5. 合并执行

主会话在集成分支执行：

```bash
git -C <target-repo> merge --ff-only <branch>
```

仅当目标仓库政策要求保留合并节点时使用 non-fast-forward merge，并记录原因。禁止 worker 执行 merge、rebase、push 或强制改写历史。

## 6. 合并后验收

1. 在集成分支复跑 WO 验收命令。
2. 运行仓库全局必需检查。
3. 检查合并后状态和变更清单。
4. 记录合并 commit、验收结果和行为变化。
5. 验收通过后将 WO 置为 `completed`。
6. 任一合并后检查失败时，优先新增修复 WO；不得在集成分支直接修补。

## 7. 冲突处理

1. 冲突发生时停止，保留冲突现场。
2. 记录冲突文件、双方来源分支和冲突内容摘要。
3. 不执行破坏性 reset、checkout 或强制覆盖。
4. 冲突解决方案需回到对应 WO 或新增 WO 声明。
5. 重放依赖方验收后再继续合并。
