# 协作执行体治理

本协议治理 WO / 开发子任务的执行体选择、降级、留痕和收口。圆桌分析会话不属于 WO 执行体，见 [roundtable-protocol.md](roundtable-protocol.md)。

## 1. 默认与优先级

1. 目标仓库显式执行体政策优先。
2. 用户明确指令优先于仓库默认，但不得违反安全底线。
3. 无目标政策和用户指令时，主会话串行执行。
4. 不因吞吐压力把可见分析会话、后台进程或普通命令输出伪装成执行体。

执行体模式：

| 模式 | 含义 | 使用条件 |
|---|---|---|
| `main-session-serial` | 主会话串行执行 | 默认；目标政策缺失、执行体能力缺失或任务不适合隔离 |
| `invisible-executor` | 主持人会话内置不可见子代理或用户确认的等价受控执行器 | 目标仓库要求 WO 执行体不可见 |
| `visible-subagent` | 客户端原生 visible child | 目标仓库明确允许或首选可见子智能体 |
| `independent-worker` | 独立 worker 会话 | 目标仓库允许，或作为真实 child 启动失败后的一次性兜底 |
| `claude-subagent` | 由宿主平台子代理工具启动的后台子代理 | 目标仓库政策允许该执行体，且宿主平台提供真实子代理工具 |

## 2. 启动前检查

1. 读取目标仓库 `AGENTS.md`、流程规范和工单中的执行体政策。
2. 确认用户是否显式指定执行体或模型。
3. 确认 WO、分支、worktree、允许修改文件、验收命令和输出位置完整。
4. 确认执行体工具真实可用。
5. 确认目标政策允许当前执行体类型。
6. 确认文件范围不与其他 active WO 重叠。

任一条件缺失时使用主会话串行、停止询问或登记延期；不得静默替换执行体类型。

## 3. 身份与启动证据

每次执行体分发必须记录：

```text
WO：
TD：
executor_type：
launch_method：
executor_id：
visibility：
model：
parent_execution_id：
subagent_start_status：
branch：
worktree：
allowed_files：
output_location：
status：
started_at：
ended_at：
```

规则：

1. `visible-subagent` 只能来自客户端原生 child 创建能力，例如 `collaboration.spawn_agent`，并记录真实 parent/child 关系。
2. `app-server thread/start` 或其他独立会话启动方式是 `independent-worker`，不得登记为 `visible-subagent`。
3. `invisible-executor` 必须是主持人内置不可见子代理或用户确认的等价受控执行器。
4. `subagent_start_status=started` 必须有真实启动响应或平台元数据。
5. 模型、任务边界、输出位置不得由主会话推测代填。
6. `claude-subagent` 只能由宿主平台子代理工具真实启动，`launch_method` 记录实际工具方式；必须登记真实 task id、实际模型、prompt 摘要、输出文件、worktree 和 allowed scope。
7. `claude-subagent` 的真实 task id 是关闭与报告核对的身份依据，不得用自造名称、会话标题或主会话推断替代。

## 4. 一次性兜底与无 fallback 路径

只有目标政策允许、且真实 child 启动失败时，才允许从 child 降级为 independent worker。

**Claude 路径无 fallback：** 一旦工单选择 `claude-subagent`，不得降级为 independent worker、可见 child、普通命令、后台进程或主会话代执行。子代理工具不可用、启动失败、执行失败或中断时，保持 `failed` / `interrupted`，登记证据并停止或返回分发方重新裁决；不得静默替换执行体。

必须记录：

```text
executor_type=fallback-worker
launch_method=<independent-worker-launch-method>
subagent_start_status=failed
subagent_start_error：
fallback_reason：
worker_id：
worker_model：
worker_scope：
worker_output：
```

以下情况不构成 child 启动失败：

1. 主会话调用参数错误。
2. 主会话误触发无关工具。
3. 任务暂停、用户转向或证据不足。
4. 未尝试启动 child。

不允许连续兜底。fallback worker 结束后不得再启动第二个 fallback 替代同一 WO；继续执行只能回到主会话串行或重新按目标政策启动合格 child。

## 5. 状态与收口

状态只允许：

```text
running / completed / failed / interrupted
```

执行结束或确定终止后必须记录：

1. 最终状态。
2. 验收结果或失败原因。
3. 输出位置。
4. 范围外发现。
5. 未完成项。
6. 文档逻辑归档声明。
7. 关闭、归档或终止执行体的证据。
8. `close_method`：实际关闭方式及对应证据位置。

`close_method` 描述如何证明执行体已经收口，不是把状态字段改为 `completed`。`claude-subagent` 的关闭证据必须是双证据：宿主平台完成通知，以及实施报告已入仓的可追溯文件与提交记录；两者缺一不得关闭。完成通知必须能关联真实 task id，入仓报告必须包含该执行体自己的验收结果。

收口证据包括平台响应、会话状态、最终消息、归档响应或目标仓库要求的等价记录。归档或关闭失败必须登记待确认事项，不得伪造成功。

## 6. 禁止事项

1. 用 shell 后台进程、普通命令输出或主持人自答冒充模型执行体。
2. 把 independent worker 登记为 native child。
3. 在目标政策禁止可见执行体时改用可见 worker。
4. 未证明 child 失败就使用 fallback。
5. 主会话代填执行体验收结果。
6. 执行体结束后不记录收口证据。
7. 用圆桌分析会话承担 WO 实施工单。

## 7. 与工单和 registry 的关系

1. 主会话仍是唯一发号和 registry 写入方。
2. 执行体只使用 prompt 中显式给定的 WO/TD。
3. WO 保持 `active` 直到验收和执行体收口完成。
4. 合并后才能置为 `completed`。
5. 执行体身份记录可保存在 WO 的执行记录、独立过程文档或目标仓库指定的治理台账，但必须可追溯。

## 8. 主会话铁律（同步自来源仓库 2026-11-17 裁定）

主会话是协调与收敛点，不是执行器。以下为无条件约束，不因任务紧急降级：

1. **主会话禁止执行长任务**。长任务=全量回归、多批冒烟、装机、打包、任何预计超 5 分钟的计算。除非用户本人明确同意，长任务必须派给真实子代理执行。主会话被长任务占住=全项目协调停摆，调度消息排队堵塞。
2. **两级派活**：主会话派子任务优先用可见子会话（用户可打开、可干预、可停止，过程透明）；可见子会话内部再派子任务优先用后台任务（保持能接收主会话调度）。层级到二级为止，禁止三级嵌套。
3. **主会话保持可接收调度**。每个非平凡动作（合入、放行、立号）完成后即检查新消息再继续；裁决与分工类消息优先处理。
4. **死线窗口只走关键路径**。旁支任务列可见清单，放行信号后统一做；任何开发动作先书面方案经用户确认。
5. **拿不准就问治理角色**。任何执行体对「这件事该不该自己做、该谁做」拿不准时，一律先问治理裁定，不得自行推断后直接动手；24 小时未答再升级问用户。

与第 2 节的关系：铁律 1 与「无政策时主会话串行」的边界是——默认串行路径适用于轻量任务；一旦构成「长任务」定义，即使无目标政策也必须外派，不得以串行名义占住主会话。

## 9. 缺陷闭环（同步自来源仓库 2026-11-18 裁定）

用户反馈缺陷采用独立台账闭环，与 WO 体系并行：

### 缓冲段：反馈先验证后立行

1. 用户每次反馈先落缓冲段（原话+场景），状态只有 `待验证 / 已处置`。
2. **复现验证通过才立缺陷行**；未复现或无法复现的反馈永远停留缓冲段，不立缺陷行。
3. 不成立的反馈必须回执用户判定依据；用户不认可可复议。

### 缺陷行规则

1. 缺陷独立编号（如 `BUG-xxx`），由发号器原子发放，与 WO/TD 同锁；禁人工翻册取号、禁复用已关闭编号。
2. 状态闭集：`待修复 → 开发完成 → 测试通过 → 已关闭`，另有 `挂起`（非终态）。
3. **换档必带证据**（日期+换档人+证据），缺证据一律拒绝换档。
4. **复测强制卡点**：缺陷进「测试通过」档只能由独立测试执行体按用户反馈场景逐条复测进入，不采信开发自证。
5. **已关闭唯一出口=用户本人验收**，任何执行体无权代关；测试通过也不算关闭（测试可能漏用户反馈的边角场景）。
6. 缺陷状态只随「测试通过/用户验收」推进，不随关联 WO `completed` 联动。

### 话术红线

「开发完成」禁说「已修复」——向用户汇报只能说「开发完成，待测试复测」；测试通过后也只能说「测试线复测通过，待用户验收」；「已修复/已解决」话术在已关闭档之前一律禁用。
