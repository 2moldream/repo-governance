# 自动圆桌讨论协议

圆桌用于重大决策、根因不明、多方案取舍、结果异常或发布风险不确定且现有证据不足以直接裁决的场景。圆桌只做分析和质疑，不执行 WO、不修改仓库。

## 1. 触发条件

满足以下任一条件，且主持人不能凭现有证据直接裁决时触发：

1. 重大架构、流程或发布决策。
2. 缺陷根因不明确。
3. 多个可行方案代价或风险差异显著。
4. 审核、测试或业务结果异常。
5. 发布、回滚或生产风险不确定。
6. 目标仓库规范明确要求圆桌。

证据已充分、目标仓库已有明确裁决、或用户已给出直接指令时，不触发圆桌；不得用圆桌延迟已明确的工作。

## 2. 参与者

1. 默认使用两个相互独立的模型分析者。
2. 模型名遵循目标仓库配置或用户显式指令；本 Skill 不内置模型名。
3. 无模型配置时先询问用户，不得自行挑选并声称是默认规则。
4. 优先使用可见子智能体；真实 child 启动失败时才允许按目标政策用独立 worker 兜底。
5. 记录会话或子智能体 ID、实际模型、任务边界、证据集和输出位置。

## 3. Round 1：独立评审

先创建全部分析者，再连续下发任务。两个分析者获得同一内容：

1. 主题和裁决问题。
2. 背景与目标。
3. 只读边界。
4. 同一证据集。
5. 约束和候选方案。
6. 禁止修改项。
7. 输出位置。

Round 1 中双方不得看到对方结论。输出必须包含：

1. 判断。
2. 证据依据。
3. 风险和反方观点。
4. 证据缺口。
5. 建议验证动作。

## 4. 主持收敛

主持人只汇总：

1. 共识。
2. 分歧。
3. 证据缺口。
4. 需要交叉挑战的问题。

不得在 Round 1 后把单方结论当作圆桌结论。

## 5. Round 2：交叉互评

Round 2 必做。主持人把双方 Round 1 结论、关键证据和分歧点交叉发给对方，要求：

1. 逐项挑战对方判断。
2. 解释分歧原因。
3. 修正或坚持原结论。
4. 标注仍缺失的证据。

没有 Round 2 的输出只能称为独立评审初稿，不得称为完整圆桌结论。

## 6. 追加轮次

Round 2 后仍存在实质分歧、出现新证据、方案重大变化或用户提出新裁决条件时，可追加聚焦轮次。

追加轮次必须：

1. 限定待裁决问题。
2. 只提供新增相关证据。
3. 明确停止条件。
4. 不无限泛化讨论。

## 7. 结论沉淀

每轮原始输出必须保留。最终收敛稿写明：

```text
主题：
轮次：
参与模型：
会话/子智能体 ID：
结论：
共识：
分歧及原因：
证据依据：
证据缺口：
后续动作：
保守兜底：
用户确认需求：
```

仍无法一致时采用 fail-closed 方案，并登记待确认事项。

## 8. 归档与终止

全部轮次结束，或因 `failed`、`interrupted`、证据缺失确定终止后，主持人必须：

1. 完成结论、失败原因、后续动作和兜底记录。
2. 归档本次创建的全部可见子智能体或 worker。
3. 记录每个会话的归档响应或状态。
4. 归档失败时保留 ID 并登记待确认，不得伪造成功。
5. 归档成功也不得删除或覆盖原始输出。

不得用 WO 执行体替代圆桌分析者，也不得把圆桌分析者用于代码修改。
