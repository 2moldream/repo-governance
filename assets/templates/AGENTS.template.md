# AGENTS.md - {{repository_name}} 开发治理

本仓库使用 L1 治理基线。保留仓库专属规则，不把流程约定扩大成无关重构。

## 1. 先方案后开发

任何行为、代码、模板或自动化变更都需要：

1. 在 `docs/design/` 下写设计或根因文档。
2. 获得用户确认。
3. 在 `docs/workorders/` 下建工单。
4. 只在工单范围内实现。

缺陷或指标回退必须先复现、定位责任环节和代码位置、记录证据与根因；不得凭经验直接修补。

## 2. 工作项

1. 实施工单使用 `WO-xxx`，开放事项使用 `TD-xxx`。
2. 编号是共享资源，只由主会话分配。
3. 并行会话不得自行推导编号。
4. 实现前先提交工单占位。
5. 已放弃编号永不复用。

共享发号器落地前，编号记录在 `docs/design/全局待办登记册.md` 和当前工单。

## 3. 分支与范围

1. 一张工单一个分支：`wo/<编号>-<slug>`。
2. 记录 base branch 或 base commit。
3. 每张工单包含 `范围内文件` 清单。
4. 清单外文件不得修改。
5. 范围外问题只写入发现，不顺手修复。
6. 集成分支为 `{{integration_branch}}`，不允许直接提交实现。

## 4. 变更契约

每张工单必须声明：

1. 背景。
2. 根因，或说明为何不适用。
3. 允许修改文件。
4. 行为变化，或明确零行为变化。
5. 验收命令。
6. 回退方案。
7. 范围外发现。
8. 实施与验收记录。

## 5. 关键治理文档评审

关键治理文档包括：

1. `AGENTS.md`、`CLAUDE.md` 等代理执行规范。
2. `docs/README.md`、文档地图、治理规范和代码地图。
3. 工单、验收、发布和协作流程模板。

修改关键治理文档前，必须先在工单中提交评审记录，覆盖：

1. 与现行规则的冲突和裁决。
2. 合理性与影响面。
3. 开发流程和工具门禁。
4. 子智能体、worker、fallback 和归档收口。
5. 发布、生产包和历史兼容。
6. 回退方案。
7. 用户或架构师确认来源。

未修改关键治理文档的工单也必须记录“不适用”及原因；评审提交必须先于实现提交。

## 6. 协作执行体与圆桌

1. 默认执行体为主会话串行；不启动 worker、子智能体或后台进程。
2. 启用其他执行体前必须单独设计和确认，并记录 WO、执行体类型、启动方法、执行者 ID、可见性、模型、分支或 worktree、允许修改范围、输出位置和状态。
3. Native visible child 必须有真实父子关系和启动证据；独立 worker 不得登记为 native child。
4. 只有真实 child 启动失败才允许一次性 fallback，并记录失败证据、原因、worker 身份和输出位置。
5. 执行结束或终止后必须记录关闭、归档或逻辑收口证据；失败登记待确认。
6. 重大决策、根因不明、多方案、结果异常或发布风险不确定时触发圆桌。
7. 圆桌使用两个独立模型分析者；模型未配置时先询问用户。
8. 圆桌必须完成 Round 1 独立评审和 Round 2 交叉互评，保留每轮原始输出。
9. 圆桌结束后归档全部可见子智能体或 worker；归档失败登记待确认，不得伪造成功。
10. 不得用 shell 后台进程、普通命令输出或主持人自答冒充模型执行体。

## 7. 验收

1. 执行工单声明的命令。
2. 逐条记录命令和结果。
3. 优先使用仓库既有检查：

```bash
{{verification_commands}}
```

4. 必需命令未执行时不得声称完成。

## 8. 配置治理

1. 每类配置必须有一个主事实源，并记录 example、运行来源、优先级、安全默认值和校验方式。
2. 并发、批次、队列、重试、超时、轮询和等待上限不得散落在业务常量、多个 env 文件或一次性命令导出中。
3. 仓库提交配置 example、schema 和默认值；本地或生产运行值不入 Git。
4. secret、端点和凭据只通过受保护运行时注入，不得提交、复制或输出。
5. 缺配置时使用保守安全默认值，不得变成无限制、无等待或自动通过。
6. 触及配置键、默认值、优先级、校验或敏感输入时，工单必须声明 `配置影响=有`。

## 9. 架构与代码结构

1. 依赖方向保持单向：Interface / Entry -> Application / Use Case -> Domain / Policy -> Infrastructure / Adapter。
2. 入口只做参数解析、帮助信息和命令分发；业务规则放入领域或应用模块。
3. 领域层不直接发起网络、数据库、文件系统、消息队列或子进程副作用。
4. 外部调用统一经过 adapter/gateway，并具备超时、错误分类、取消和可追溯标识。
5. 禁止新增循环依赖、反向依赖、无归属公共模块和长期动态加载别名。
6. 修改前说明文件或模块当前职责；新增行为不属于该职责时，放入边界清晰模块。
7. 已识别巨石内禁止新增业务逻辑；只允许薄 adapter、委托或净删除。
8. 巨石迁移按行为切片进行，先建立 characterization test，再做等价对照。
9. 兼容 shim、影子实现和动态 import 别名必须记录原因、替代路径、删除条件和承接工单。
10. 触及入口、模块边界、依赖方向、外部 IO、状态机、schema、巨石或兼容层时，工单必须声明 `架构影响=有`。

## 10. fail-closed 汇报

1. 缺证据一律 `需确认`，不得按通过处理。
2. 不得为通过检查静默缩小范围。
3. 开放事项没有验收证据不得关闭。
4. 未验证的迁移、发布或恢复不得声称完成。
5. 实现未完成时，明确剩余工作和原因。

## 11. 默认不启用

以下能力需单独设计和工单确认：

1. 多 worker 分发。
2. 多 worktree 执行。
3. 长期分支与合并自动化。
4. 文档/代码地图门禁。
5. 发布证据自动化。
6. 巨石规模 ratchet 与结构自动门禁；启用前先建立目标仓库基线。
7. 独立执行体调度；主会话串行是默认安全路径。
