# 方案：repo-governance Skill 初始化与仓库适配

## 元信息

- 状态：active，方案方向已由用户确认。
- 日期：2026-11-02。
- 当前工单：WO-001，仅建立独立仓库、方案与执行规范。
- 行为边界：本方案不实现 Skill，不安装运行时，不修改任何目标仓库。

## 1. 背景

来源项目在长期演进中形成了一套有效机制：先方案后开发、缺陷根因先行、统一工单编号、一工单一分支、多 worker 分发、多 worktree 隔离、文档事实源治理、验收留痕和 fail-closed。该机制支持多任务并行和长期追溯，但也包含大量领域专属约束，不能整体复制到所有仓库。

用户目标是把其中普适的方法论沉淀为独立 Codex Skill。下次进入开发任务时，Skill 可以根据目标仓库现状诊断或初始化治理基线，避免每次人工逐条补充规则。

## 2. 已核实现状

来源仓库截至 2026-11-02 的治理快照：

| 事实 | 数值 / 结果 |
|---|---:|
| Registry 记录 | 28 |
| WO 分支 | 129 |
| Worktree | 80 |
| Registry 冲突 | 0 |
| `docs/workorders/` 工单 | 119 |
| 文档治理检查 | pass |
| 工单治理检查 | pass |

这些数字说明统一编号、共享 registry、独立分支和 worktree 对长期并行开发有效，应作为核心能力保留。同时，来源仓库的文档、模型、数据集、业务指标和发布规则具有来源项目专属语义，不能默认泛化。

## 3. 根因

跨仓库复用当前缺少独立承载物：

```text
治理经验写在来源仓库规范中
  -> 其他仓库无法直接引用
  -> 每次人工复制部分规则
  -> 编号、分支、验收和协作协议容易缺失或不一致
  -> 并行任务出现撞号、范围重叠、合并困难和验收证据不足
```

解决方向是把方法论从来源仓库剥离成独立 Skill，并在目标仓库执行前先判断已有约束，避免模板覆盖。

## 4. 目标

1. 建成独立源码仓库 `repo-governance`，与来源项目代码分支、工单编号和发布流程隔离。
2. Skill 能识别目标仓库已有约束，输出诊断和合并方案。
3. 无约束仓库可直接建立 L1 最小治理基线。
4. 保留 L2 多 worker、L3 多 worktree / 多分支长期演进、L4 文档与发布治理能力。
5. L2/L3/L4 默认不启动，只在满足条件或用户确认后启用。
6. Skill 自身有版本、方案、工单、验收和发布记录。

## 5. 能力分层

### 5.1 L1 默认基线

适用所有开发仓库。

内容：

1. 先方案后开发。
2. 缺陷先复现和定位根因。
3. WO/TD 统一编号和共享 registry。
4. Placeholder-first。
5. 一工单一分支：`wo/<编号>-<slug>`。
6. 范围内文件清单。
7. 行为变化声明。
8. 验收命令和实施记录。
9. 范围外问题只登记不顺手改。
10. 缺证据、超范围、未验收时 fail-closed。

### 5.2 L2 多 worker 协作

状态：保留，默认不启动。

启用条件：

1. 用户明确要求并行。
2. 任务边界清晰。
3. 文件范围不重叠。
4. 主会话已统一发号和分发。

协议：

1. 主会话是唯一发号方。
2. Worker 只接收显式 WO、分支、worktree、范围、验收和停止条件。
3. Worker 禁止自行取号、改 registry、扩范围。
4. 每个会话记录标识、模型、边界、输出和状态。
5. 文件重叠任务禁止并行。

### 5.3 L3 多 worktree 与多分支长期演进

状态：保留，默认不启动。

启用条件：

1. 多工单并行。
2. 目标仓库存在活跃集成分支。
3. 单工作区容易发生覆盖或串单。
4. 用户确认使用独立 worktree。

协议：

1. 每张工单独立 worktree。
2. Registry 记录 branch、base、owner、worktree、状态和 placeholder。
3. 集成分支禁直推。
4. 合并前复跑验收。
5. 依赖任务声明合并顺序。
6. 保留脏 worktree、范围外文件和分支差异检查。

### 5.4 L4 文档与发布治理

状态：保留，默认不启动。

包含：

1. 事实源矩阵。
2. 文档地图和生命周期。
3. code map 与生成视图。
4. 工单影响门禁。
5. 发布证据链。
6. 自动治理脚本。

启用条件：

1. 长期演进仓库。
2. 多人或多 worker 并行。
3. 文档漂移已经造成误读或返工。
4. 用户明确要求强治理。

## 6. 目标仓库适配流程

### 6.1 已有开发约束

必须先诊断，不得直接套模板。

扫描对象：

1. `AGENTS.md`、`CLAUDE.md`、`GEMINI.md` 等代理规范。
2. 贡献指南、README、架构文档。
3. Issue / PR 模板。
4. CI 配置。
5. 测试和构建脚本。
6. 既有分支、标签和工单系统。
7. 目标仓库的团队角色和合并政策。

诊断输出：

| 类别 | 含义 | 处理 |
|---|---|---|
| 一致 | 内置方法与仓库规则等价 | 保留仓库原文，不重复写入 |
| 重复 | 表达不同但要求重复 | 保留更精确的一方，链接另一方 |
| 缺失 | 仓库没有底线规则 | 提议补充 |
| 冲突 | 双方规则不能同时成立 | 引用双方原文和位置，给合并方案 |
| 专属例外 | 目标仓库有明确历史或业务原因 | 保留并标注例外 |

冲突时目标仓库显式规则优先。只有安全、越权、缺证据默认通过、未验收声称完成等底线风险必须阻断。

### 6.2 无约束但已有仓库

先做轻量识别：

1. 语言和包管理器。
2. 测试命令。
3. 构建、lint、格式化命令。
4. 当前分支和脏文件。
5. 现有文档目录。
6. 是否存在外部 Issue / Jira / TAPD 系统。

然后建立 L1 最小基线，不默认创建 Heavy 文档体系。

### 6.3 空仓库或新项目

直接建立 L1：

```text
AGENTS.md
docs/README.md
docs/workorders/WO-001.md
docs/design/方案-<主题>.md
docs/design/全局待办登记册.md
```

如目标仓库已有外部工单系统，增加 `external_id` 映射，不复制双套业务流程。

## 7. Registry 数据设计

运行时 registry 保存在目标仓库 Git 共享层，不提交进业务分支：

```text
$(git rev-parse --git-common-dir)/repo-governance/workorder-registry.json
$(git rev-parse --git-common-dir)/repo-governance/workorder.lock
```

记录结构：

```json
{
  "schema": "repo-governance.workorder_registry.v1",
  "sequence": {
    "workorder": 1,
    "todo": 1
  },
  "records": [
    {
      "workorder_id": "WO-001",
      "todo_id": "TD-001",
      "status": "active",
      "owner": "main-session",
      "base": "<commit-or-ref>",
      "branch": "wo/001-example",
      "worktree": null,
      "placeholder": "<commit>",
      "external_id": null,
      "created_at": "2026-11-02T00:00:00+08:00",
      "updated_at": "2026-11-02T00:00:00+08:00"
    }
  ]
}
```

约束：

1. 状态枚举固定。
2. 编号单调递增。
3. `abandoned` 不复用。
4. `placeholder` 在实现提交前登记。
5. 多进程写入必须加锁。
6. 外部系统 ID 只做映射，不替代本地稳定 ID。

## 10. 影响面

本仓库：

1. 新增独立 Git 仓库。
2. 后续 Skill 可版本化管理。
3. 不影响来源项目工作区 分支和未跟踪文件。

目标仓库：

1. L1 会写入或合并代理规范与工单模板。
2. L2/L3/L4 默认不写入，不启动。
3. 已有约束仓库必须先输出诊断与合并建议。

## 11. 预期效果

| 指标 | 当前 | 目标 |
|---|---:|---:|
| 跨仓库治理规则复用方式 | 人工逐条复制 | Skill 诊断或初始化 |
| 并行撞号 | 依赖人工避免 | registry 加锁后为 0 |
| 工单无范围文件清单 | 常见 | L1 后为 0 |
| 工单无验收命令 | 常见 | L1 后为 0 |
| 未验收声称完成 | 依赖人工判断 | 门禁阻断 |
| 范围外修改 | 依赖人工审查 | 范围检查阻断 |
| 多 worker 伪造 | 无统一协议 | 会话与状态留痕 |

## 12. 不做什么

1. 不把来源项目数据集边界、外部执行 CLI 边界、审核指标、模型名或业务规则泛化。
2. 不默认启动多 worker、多 worktree 或 Heavy 文档门禁。
3. 不覆盖目标仓库显式规则。
4. 不把目标仓库强制迁移到来源项目目录结构。
5. 不在无用户确认时修改已有约束仓库。
6. 不把 registry 提交进业务分支。
7. 不用文档检查替代测试、lint、E2E 或业务验收。

## 13. 验收原则

Skill 后续验收必须覆盖：

1. 已有 `AGENTS.md` 仓库：只输出诊断，不直接修改。
2. 冲突规则：输出双方原文、位置和合并建议。
3. 空仓库：生成 L1 基线。
4. 编号并发申请：不撞号、不复用。
5. placeholder-first：未登记时阻断实现。
6. 范围外文件：阻断或报告。
7. L2/L3/L4：默认不启动，显式启用后生效。
8. 安装后 Codex 能按 description 正确触发。
